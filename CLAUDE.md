## What this project is

An assessment tool for **TM Forum Autonomous Network (AN) maturity levels (L0–L5)**, replacing a manual, Excel-based questionnaire process with a cloud application.

- TM Forum defines Autonomy Levels 0 (fully manual) through 5 (fully autonomous).
- CSPs (telecom operators) are assessed against these levels via standardized questionnaires per **High-Value Scenario (HVS)**.
- HVS categories span Network Layer (Fault Management, Change Management, Quality Management, Energy Management, Resource Management, Planning, Deployment) and Service Layer (Service Assurance, Complaint Handling, Service Delivery, Service Marketing, Service Fault Management), across network types (RAN, Core, IP, Transport, Fixed Access).
- Seven questionnaires exist today, across five domains: **RAN Fault Management (GB1059A)**; **Core Network Fault Management** and **Core Network Stability** (GB1059B — Stability is a precondition questionnaire, see "Core Domain" below); **IP Network Fault Management (GB1523E)**; **Transport Microwave** and **Transport OTN Fault Management** (GB1523D, two independent HVSs); and **Fixed Access Network Fault Management (GB1523C)** — see "IP, Transport and Fixed Access" below. Other HVS questionnaires (Change Management, Quality Management, etc.) do not exist yet — do not build for them speculatively.
- The core workflow being replaced: today the xlsx questionnaires are emailed to engineers per client, filled in independently, then manually collected and aggregated into a chart. The app must eliminate that manual aggregation and enable direct cross-client benchmarking.

## Domain model

### RAN Fault Management (from `RAN_FM.xlsx`)

1. **Guideline** (reference only, no data entry) — explains the Cognitive Activity model **IAADE** (Intent, Awareness, Analysis, Decision, Execution) and the 5 **sub-scenarios** derived from `alarmType` in 3GPP TS 28.111: Equipment, Processing Error, Communications, Environmental, Security. Each sub-scenario has a fixed **fault-distribution weight** (Equipment 0.15, Processing Error 0.15, Communications 0.3, Environmental 0.3, Security 0.1).

2. **`RAN - Fault Management`** (the questionnaire) — one row per question (8 rows: Intent-driven, Data collection & Alarm filtering, Fault Prediction, Fault identification & Impact analysis, Demarcation & Locating, Solution generation, Evaluation and decision-making, Solution implementation). Columns: `Cognitive Activity (IAADE)`, `Service Capability`, `Weight` (question's weight within the questionnaire, all 8 sum to 1.0), `Question` text, `Option A`–`Option D` (A = highest autonomy; some questions only have 3 options), and one **answer column per sub-scenario**. Every question is answered *once per sub-scenario*, not once overall — a full response is 8 questions × 5 sub-scenarios.

3. **Scoring** — derives numeric results from the letter answers.
   - Each question defines numeric **criteria** per option (e.g. A=4, B=3, C=0 — not evenly spaced, and not every option is used). A question's **own top score** is the highest of its option criteria (always Option A's).
   - "Original score" for a sub-scenario/question = the criteria value matching the selected letter.
   - **Compensation** (see `What is ANLET compensation.pdf`): in the AN Level score map, different cognitive-activity tasks reach full automation at different levels — most questions top out at 4, but some top out lower (in this questionnaire: Data collection & Alarm filtering and Fault identification & Impact analysis top out at 3, Solution implementation tops out at 2). When a question's original score equals **its own top score**, it is compensated: bump it up to the average of the *other* questions whose top score is the full ceiling (4), if that average is higher. Without this, a sub-scenario could never reach a perfect score just because one of its tasks has a structurally lower ceiling. This is a **general per-question rule** (`topScore` vs. `questionnaireCeiling`), not a fixed hand-picked list of "anchor" questions — `scoring.ts` derives eligibility from each question's own criteria rather than hardcoding a list, and this was validated against Core Network FM's different question set (5 anchors, 4 compensated rows vs. RAN's 5-and-3) and Core Network Stability (every question shares the same top score, so nothing ever compensates) without any code changes — only new seed data.
   - "Overall Score" per sub-scenario = weighted sum of the 8 compensated scores, weighted by each question's `Weight`.
   - **Final score** = weighted average of the 5 sub-scenario overall scores, weighted by the sub-scenario fault-distribution weights.
   - A separate "Method 2: Climbing" column set exists per question but is marked "for reference only" in the sheet — Method 1 (Average, above) is the official method to implement.

4. **`E2E Automation Ratio Checklist`** — derives an end-to-end automation ratio per sub-scenario:
   - Per question/sub-scenario cell: `S` (System) if the answer is "A", else `P` (People).
   - **The Intent question is excluded from this check** (`E2E Automation Ratio Checklist!C12`'s formula only ranges over the Awareness→Execution rows) — a sub-scenario can still achieve E2E "Y" even if its Intent answer isn't "A". Don't infer this from "all questions are A"; it's specifically all questions *except Intent*.
   - Per sub-scenario: E2E automation achieved (`Y`) only if every non-Intent question scored `S`.
   - **E2E Automation Rate** = sum of the fault-distribution weights of only the sub-scenarios that achieved `Y`.

**Golden-master test fixture** (verified against the xlsx's own demo answers — use as the first `scoring.test.ts` case): answers `[A,B,A,A,A]`, `[A,A,B,A,A]`, then all-`A` for the remaining 6 questions (Equipment/ProcessingError/Communications/Environmental/Security order) → sub-scenario scores Equipment=4, ProcessingError=3.83, Communications=3.8, Environmental=4, Security=4; **final score = 3.9145**; E2E Y/N = Y,Y,N,Y,Y → **E2E rate = 0.7**.

### Core Domain (from `CORE_FM.xlsx`)

Two independent questionnaires, both under the "Core" domain (`Questionnaire.networkType = "Core"`):

1. **Core Network Fault Management** (`CORE_FM_GB1059B`) — 9 real questions (Awareness through Execution). The sheet has a 10th row, Category "Intent", weight 0, question/options literally `"n/a"` — a non-functional placeholder (the Guideline explicitly says intent isn't included in fault management yet) and is **not seeded as a question at all**. 2 sub-scenarios: Equipment (weight 0.1) and Communication & Quality of Service (weight 0.8) — these intentionally **don't sum to 1** (same as the xlsx's own "Fault distribution (Total ≥ 90%)" convention); the final-score formula (and `scoring.ts`) normalizes by dividing by the weight sum, not assuming it's 1. Has its own E2E Automation Ratio Checklist (Intent excluded, same as RAN).
2. **Core Network Stability** (`CORE_STABILITY_GB1059B`) — 7 questions (Basic stability ×5, Intelligent stability ×2), weights summing to 1. **No sub-scenarios and no E2E checklist** — a Stability question is answered once, not once per sub-scenario. Modeled as a single synthetic sub-scenario (`code: "OVERALL"`, weight 1) so the schema/scoring engine need zero special-casing; `Questionnaire.hasE2ECheck = false` tells the frontend to hide the E2E section entirely. Every question here shares the same top score (4), so compensation structurally never triggers for any of them — a useful contrast case from RAN/Core FM, where it does.
3. **Core Domain combined score** (Guideline point 7): *"final score = 50% × fault management score + 50% × stability score"*. Computed **per-user**, once they've submitted both questionnaires (`responses.service.ts`'s `getCoreDomainSummary`) — not an org-wide aggregate. Shown on the results page for either Core questionnaire once both are submitted; shows which half is still missing otherwise.

### IP, Transport and Fixed Access (from `IP_FM.xlsx`, `Transport.xlsx`, `Fixed_Access.xlsx` — see `NEW_HVS_PLAN.md`)

All four questionnaires share one sheet layout (question columns B-I plus a block of per-sub-scenario answer columns under name/weight header rows), so `prisma/seed/fmSheetParser.ts`'s `readFmSheets(workbook, layout)` does the reading and `parseIpFmXlsx.ts` / `parseTransportXlsx.ts` (Microwave + OTN) / `parseFixedAccessXlsx.ts` only supply row/column offsets plus their own guideline mapping. **No scoring-engine changes were needed** — `scoring.ts`'s general compensation rule covers every new questionnaire (top scores of 3 or 2 compensate against the average of the top-4 questions, Intent included).

- **Codes/domains**: `IP_FM_GB1523E` (networkType `IP`), `TRANSPORT_MW_FM_GB1523D` + `TRANSPORT_OTN_FM_GB1523D` (`Transport`; both use hvsCategory "Fault Management" so the HVS-first picker shows Fault Management → Transport Domain → Microwave / OTN; **no combined Transport score** — the source defines none), `FIXED_ACCESS_FM_GB1523C` (`Fixed Access`). Sub-scenario codes are derived from the names (`toSubScenarioCode`).
- **E2E**: IP and Fixed Access have checklists (Intent excluded, as RAN/Core); Transport has none → `hasE2ECheck = false` for both.
- **Sub-scenario categories**: new nullable `SubScenario.category`, read from the merged header row above the sub-scenario columns (IP: Equipment / Communication / Quality of service; Microwave and OTN: Communication / Equipment / Environmental). Null for RAN, Core and Fixed Access. `frontend/src/lib/subScenarioCategories.ts` drives grouped header rows (`ScoreBreakdownTable`, `E2EChecklistTable`), a full-width category heading row above each group in `QuestionCard`'s answer table (a column there squeezed the sub-scenario names, since the radio cell can't wrap), a merged Category column in `ScoreSummary`, category sub-headings (`AnswerDistributionDrilldown`) and a "Category · Name" flat label (benchmark columns, Excel/PDF exports, Comment Collection). Every helper degrades to the original flat rendering when no category exists.
- **Guideline content**: IP's context sheet is "Introduction" (no per-question guidance — question "Note:" text stays inline in the question). Fixed Access's section III has 8 rows for 9 questions with shifted Service Capability labels — rows are mapped **by their question text**, guarded by a must-contain phrase so a revised file fails loudly; Fault Prediction has no guidance. Transport's shared section III matches Microwave's 9 questions in order; OTN skips the Microwave-only "Intent Fulfilment" row.
- **Known source defects, deliberately not replicated** (each parser's header comment has details): IP's questionnaire tab lacks inline criteria for Solution Generation and Awareness option D (Scoring sheet used, as always); Scoring_Microwave has a copied "compensate if = 3" formula on Intent Fulfilment (top score 4) and its Execution average omits Intent Fulfilment, and its KEI block is broken (`#REF!`); Fixed Access's E2E "achieved" formula ranges over `C6:C12`, also excluding Data Collection — the general Intent-only exclusion is used; Scoring sheets that score an option the question doesn't offer (Fixed Access Execution D=0) are dropped by `criteriaForOfferedOptions`.
- **Golden masters**: each parser test runs the workbook's own demo answers through `computeScoreResult` (`demoAnswers.testUtils.ts`) and compares with Excel's cached values — IP 0.9 / E2E 0, Fixed Access 4.0 / E2E 1, Microwave sub-scenarios 4 / 2.7 / 1.7 (its 4th demo column answers D on A-C-only questions, unreachable in the app), OTN's single answered sub-scenario 0.9.

### Key Effectiveness Indicators (KEIs, `NEW_HVS_PLAN.md` Phase B)

Outcome measures (MTTR, automation/diagnosis ratios) listed under each source's questionnaire tab — IP (3), Transport Microwave (2) and OTN (4); RAN, Core and Fixed Access have none. Answered **once per response** (not per sub-scenario) on an A-C range scale, criteria 4/3/2 from the Scoring sheets (weights from the questionnaire tab — Scoring_Microwave's KEI weights point at the OTN sheet and its score is `#REF!`).

- **Model**: `EffectivenessIndicator` (per questionnaire, option text/criteria like `Question`), `ResponseKei` (`selectedOption?`, free-text `indicatorValue?`, `comment?` — all nullable; an all-empty save deletes the row), `ScoreResult.keiScore`, `Questionnaire.keiNote` (the source's "values are for pilot use" note). Parsed by `fmSheetParser.ts`'s `readKeis`, which cross-checks each Scoring-sheet row's name against the questionnaire row.
- **Score**: `scoring.ts`'s `computeKeiScore` — weighted average of answered KEIs, re-normalized over skipped ones, `null` when none are answered or there are no KEIs. **A separate "Effective Indicator score", never blended into `finalScore`** (per product decision). Golden master: IP_FM.xlsx demo B/C/C → 2.4.
- **Mandatory, skippable with a comment**: `submitResponse` blocks (same 422 `UncoveredSkipError`, now with `missingKeis`) any KEI that has neither an answer nor a non-blank comment. A measured value alone does not cover a KEI.
- **UI**: a "Key Effectiveness Indicators" step between the last question and Review (`KeiStep`/`KeiCard`; one local state object + single save path per KEI, like `QuestionCommentEditor`, with radio clicks flushing pending text and a pending save **flushed on unmount** rather than dropped — verified in the browser); Review lists uncovered KEIs as jump links; results show the KEI score beside the capability score plus `KeiResultsTable`; Executive/Deep-Dive get `KeiDistribution` (counts incl. "Skipped", per-respondent value/comment, NatCo scoping), an "Avg. KEI score" benchmark column (`showKeiColumn`, Admin too), KEI comments in every Comment Collection (Cognitive Activity "Effectiveness Indicator", Sub Scenario = KEI name — `lib/keiDistribution.ts`), and KEI sheets/sections in the Excel/PDF reports.

### Super admin, role changes, CSV template, support contact (`ADMIN_MANAGEMENT_PLAN.md` Phase 1)

- **Super admin** is `User.isSuperAdmin` on an `ADMIN` account (a flag, not a `Role` value, so every existing `requireRole('ADMIN')`/`role === 'ADMIN'` check keeps admitting it). Set only by the seed, on the bootstrap `ADMIN_EMAIL` account (production: `jaserbin.rahman@detecon.com`); never changeable through the API.
- **Role rules** (`users.service.ts`, re-reading the caller from the DB rather than trusting the JWT): any admin may switch a user between Normal User and Executive; granting/removing Admin, creating an Admin, and editing or deleting another admin account are super-admin-only (`SuperAdminRequiredError` → 403); the super admin account is never modifiable (`CannotModifyAdminError`); nobody changes their own role (`CannotChangeOwnRoleError`). `listUsers` now includes admins (with `isSuperAdmin`) so the Manage users table can show them read-only or editable per those rules. Demoting an Admin to Normal User re-triggers the normal profile-completion redirect.
- **Bulk CSV template**: `BulkCreateUsersForm`'s "Download CSV template" writes the exact `email,role,organization,password` header plus two example rows (using a real organization name). Bulk roles stay Normal User / Executive.
- **Support contact**: `components/SupportContact.tsx` (single `SUPPORT_EMAIL` constant) on the login page (and referenced from the login error), forgot-password and reset-password pages.
- **External people** (e.g. a contractor working for one client) are **Executives of that client's organization**, not admins — Executives already see only their own organization. Projects / external admins (plan Phase 2) were cancelled; Admin is Detecon-internal only.
- Not built yet: production SMTP (plan Phase 3 — the forgot-password flow exists but production still points at a placeholder SMTP host).

### Multi-organization memberships, working context, temporary passwords (`MULTI_ORG_PLAN.md`)

- **`Membership`** = `{ userId, organizationId, role (EXECUTIVE|NORMAL_USER), opCoId?, workingDomain?, designation? }`, unique per (user, organization). `User.role` now only means global **Admin or not** (`ADMIN`/`NORMAL_USER`); `User.organizationId` is just the home org. The NatCo/Working Domain/Designation profile moved from `User` to `Membership` (completed once per organization, via the active membership).
- **Working context**: the JWT carries `membershipId` (null = admin context or default). `middleware/auth.ts` re-resolves it from the DB on every request (`lib/userContext.ts`'s `resolveRequestUser`) into `req.user = { sub, email, role, organizationId, membershipId, isAdmin }` — role/org are the *active context's*, so existing role/org checks work unchanged. Invalid/foreign membership ids fall back to the default (admin context for admins, else the oldest membership). `POST /api/auth/context` switches; `/api/auth/me` returns `contexts`/`activeMembershipId`/`isAdmin`. Frontend: `/context` picker after login when there's more than one context, and a "Working as" `ContextSwitcher` in `AppHeader` (switching clears the query cache and goes Home).
- **Responses belong to a membership** (`@@unique([membershipId, questionnaireId])`): the same person answers separately per organization; `assertAccepting` uses the response's membership org. All `insights` analytics group by membership (org/NatCo/profile).
- **Admin rules** (`users.service.ts`): any admin adds/changes/removes Executive/Normal User memberships of non-admins (an admin account's memberships: super admin or that admin); granting Admin is super-admin-only. Removing a membership is blocked only if it has a response *with data* (`RESPONSE_WITH_DATA`: submitted or any answer/comment/KEI) — empty IN_PROGRESS responses (created just by opening a page) are deleted along with it. Creating a user / bulk-CSV row with an existing email adds a membership (password unchanged).
- **Temporary password**: `POST /users/:id/temporary-password` generates one, sets `mustChangePassword`, returns it once (shown in `ManageUsersSection`). Any admin for non-admins; only the super admin for another admin; never for the super admin or yourself.
- Migration `20261005090000_add_memberships` converts each existing non-admin user (and any admin with responses, as Executive) into one membership with id `'m_' || md5(userId)` and `createdAt` = the user's own `createdAt` (not `CURRENT_TIMESTAMP`, which would make it sort after later-added memberships and break the default context).

### Org hierarchy and profile completion (from `FIRST_REVIEW.md`)

Real-world usage feedback after the MVP demo described large CSP groups with multiple NatCos/OpCos per Organization, and users self-identifying their Country/Company/Working Domain/Designation before answering. Decisions locked in for this:

- **`OpCo`** (NatCo) is a new, formal, Admin-managed entity between `Organization` and `User` (`{ id, name, country, organizationId }`, unique per `[organizationId, name]`) — not free-text profile fields. Benchmarking groups by this controlled entity (see "Multi-level benchmarking" below), not user-typed strings, which would drift (typos, inconsistent naming).
- **No open self-signup.** Admin still creates every login (email/password/role/Organization) exactly as before. `opCoId`/`workingDomain`/`designation` (now on `Membership`, see above) are nullable, filled in by the user themself via a one-time **profile-completion** step after first login (`PUT /api/auth/profile`, `ProfilePage.tsx`) — picking their OpCo from a dropdown scoped to their own `organizationId` (`GET /api/opcos?organizationId=...`), plus free-text Working Domain/Designation. `ProtectedRoute.tsx` redirects any `NORMAL_USER` with `opCoId == null` to `/profile` before they can reach any other route; Executives/Admins never need this (they don't answer questionnaires). `GET /api/auth/me` reads fresh from the DB rather than only echoing the JWT payload, specifically so profile completion is reflected immediately without requiring a fresh login/token.

### Per-question comments and skips (from `FIRST_REVIEW.md`)

The questionnaire UI is **question-major**, not sub-scenario-major: each step shows one question, its options, once — followed by one A–D dropdown per sub-scenario (`QuestionCard.tsx`), instead of repeating the whole question once per sub-scenario. A dropdown's default "— Not answered —" state (or reselecting it) represents a **skip** — `DELETE /responses/:id/answers/:questionId/:subScenarioId` (`responses.service.ts`'s `deleteAnswer`) removes a previously-saved Answer row, since answering is no longer one-directional.

- **One comment per question per response** (`QuestionComment` + join table `QuestionCommentSubScenario`), optionally tagged to specific sub-scenarios or explicitly to "None of the sub-scenarios" (`appliesToNone`). Always available as a general annotation, but **mandatory to cover a skip**: at submit time (`responses.service.ts`'s `submitResponse`), every `(question, subScenario)` pair with no answer must be covered by a comment **explicitly tagged to that specific sub-scenario** — otherwise submission is blocked with `UncoveredSkipError` (422, carrying the specific missing list). `appliesToNone` does **not** satisfy this (THIRD_REVIEW.md Phase 1 tightened this from the original "tagged to that sub-scenario, or `appliesToNone`" rule — see "Mandatory sub-scenario tagging" below); it remains a valid flag for a comment unrelated to any skip. Not blocked question-by-question while answering; the user can navigate freely and only sees the gap list on the pre-submit **Review step** (`ReviewStep.tsx`), which also lists every comment before Submit is enabled.
- **Skip scoring**: `scoring.ts`'s `computeScoreResult` no longer throws on a missing answer — it excludes that question from the sub-scenario's weighted average and **re-normalizes** by dividing by the *answered* questions' weight sum (not the full questionnaire's), so a partial response still produces a meaningful score. If every question in a sub-scenario is skipped, its `overallScore` is `null` (not 0) and it's excluded from the final-score weighted average the same way; if literally everything is skipped, `finalScore` falls back to 0 rather than `NaN`. Compensation only considers *answered* anchor questions.
- **E2E display**: a skipped cell renders as `–` (distinct from `S`/`P`) in `E2EChecklistTable.tsx`, and counts as "not System" for the Y/N determination — a sub-scenario with any skipped non-Intent question can never achieve E2E "Y". Only a display/classification change; the E2E rate formula itself is untouched.
- **Real bug caught by browser testing, not tests**: `QuestionCommentEditor.tsx` originally read sub-scenario tags off the `comment` prop while keeping only the text as local state. Clicking a tag checkbox while the comment textarea was focused blurs the textarea *first* (before the checkbox's own `onChange`), and that blur handler's save could race the checkbox's save over the network — whichever request's response arrived last would silently win, sometimes dropping the just-checked tag. Fixed by keeping the **entire** `CommentState` (text + tags + appliesToNone) as one local state object with a single debounced save path, so there's only ever one save in flight per burst of edits, always containing the full latest state. Same class of lesson as the router-mounting/route-ordering gotchas below: a plausible-looking data flow that only breaks under a specific interaction order, invisible to unit tests.

### Terminology, weight/criteria visibility, and Cognitive Activity restructuring (from `SECOND_REVIEW.md`, Phases 1-3)

- **"Unanswered" vs "skipped"**: reserved terms now, used consistently. "Unanswered" = a `(question, subScenario)` pair with no answer, full stop. "Skipped" = unanswered *and* covered by a comment (submittable, scored via re-normalization — see above). An unanswered pair with no covering comment blocks submission and is never called "skipped" in user-facing text. `E2EChecklistTable.tsx`'s `–` cell and its legend, `ReviewStep.tsx`'s counts, and `UncoveredSkipError`'s message text all follow this distinction (the `UncoveredSkipDto`/`UncoveredSkipError` *identifiers* were kept as-is — renaming them was pure churn — only their user-facing strings changed).
- **Weights and option criteria are now shown to the user while answering** (`QuestionCard.tsx`): each question's own weight, each sub-scenario's `faultDistributionWeight`, and each option's numeric criteria (e.g. "A (4)") are all rendered inline. The criteria-number display is a **deliberate reversal** of the prior anti-gaming stance — `questionnaire.service.ts` used to strip `optionACriteria`..`optionDCriteria` from `QuestionDto` specifically so a user couldn't just pick the highest-scoring option without reasoning about the question; per an explicit product decision this protection was traded for scoring transparency. If this is ever questioned, it's intentional, not a regression.
- **Cognitive Activity (IAADE) grouping**: `frontend/src/lib/cognitiveActivity.ts`'s `groupByCognitiveActivity()` groups a questionnaire's questions by `cognitiveActivity` (relying on `sortOrder` already following IAADE order, so activities land in contiguous runs), with each group's question count and combined weight. Shared by `QuestionStepper.tsx` (the question-answering nav, e.g. "Awareness — 2 questions, 35%") and `ExecutivePage.tsx`'s answer-distribution table (a group header row per activity, Service Capability as the row underneath).
- **Per-question score breakdown**: `scoring.ts`'s `computeScoreResult` now also returns `questionScores: QuestionScore[]` — one entry per `(question, subScenario)` pair (including unanswered ones, both scores `null` there) carrying `originalScore` and `compensatedScore`, the exact value that feeds into the sub-scenario's weighted-average `overallScore`. Persisted at submit time via the new `QuestionScoreResult` table (one row per `(question, subScenario)`, FK'd to `ScoreResult`) — a write-once snapshot like `SubScenarioScoreResult`, not recomputed live on read. `ScoreBreakdownTable.tsx` renders this as the results page's **primary table** (replacing `ScoreSummary` in that role): one row per question grouped by Cognitive Activity, one column per sub-scenario, cell = compensated score or `–` for a skip. `ScoreSummary` (the original sub-scenario-level Weight/Score table) stays as a secondary rollup beneath it (`hideFinalScore` prop added so the headline number isn't shown twice).
- **Postgres row-order gotcha, caught while building the above**: `getResult`'s Prisma queries for `subScenarioScores`/`questionScores` (and `submitResponse`'s own `questions`/`subScenarios` fetch) originally had no `orderBy` — Postgres doesn't guarantee row order without one, and a DB-backed integration test comparing the freshly-computed result against the persisted-then-reread result (`toEqual`, order-sensitive) flaked because of it. Fixed by adding explicit `orderBy: { sortOrder: 'asc' }` (and, for `questionScores`, ordering by the related `subScenario.sortOrder` then `question.sortOrder`) everywhere a `ScoreResultDto` is assembled from the DB, so persisted order always matches `computeScoreResult`'s emission order. Not caught by a first test run — surfaced on a later, unrelated rerun once table contents changed enough to perturb physical row order.

### Guideline content (from `SECOND_REVIEW.md`, Phase 4)

- `Questionnaire.guidelineText` (questionnaire-level context) and `Question.answeringGuideline` (per-question guidance) are both extracted directly from each xlsx's `Guideline` sheet by the parsers — never fabricated. RAN_FM.xlsx's Guideline sheet has both: Sections I/II (Introduction + Sub-scenarios, `parseRanFmXlsx.ts`'s `extractGuidelineText`) for the questionnaire-level text, and Section III (one row per question, "Answering Guideline" column) for the per-question text (`extractAnsweringGuidelines`, matched to questions by row order, not by fuzzy text matching — the two sheets' capitalization differs slightly, e.g. "Fault Prediction" vs "Fault prediction"). CORE_FM.xlsx's Guideline sheet only has a numbered Introduction (`extractCoreGuidelineText`, shared verbatim by both `CORE_FM_GB1059B` and `CORE_STABILITY_GB1059B`, since they share one Guideline sheet) — it has no per-question breakdown, so `Question.answeringGuideline` is `null` for every Core question; don't invent guidance text where the source doesn't have it.
- **xlsx column-offset gotcha, caught by a failing parser test, not by inspection**: RAN_FM.xlsx's `Guideline` sheet's used range (`!ref`) starts at column B, not A (unlike every other sheet these parsers read) — SheetJS's `sheet_to_json({header: 1})` arrays are trimmed to the sheet's used range, so array index 0 is column B there, not column A. Hardcoding column indices without checking each sheet's own `!ref` silently reads the wrong column (returned `null` for every cell, not an error) — verify a new sheet's `!ref` before assuming column-letter-to-array-index parity holds.
- Rendered as collapsible `<details>` sections (collapsed by default): questionnaire-level in `QuestionnairePage.tsx` above the stepper, per-question in `QuestionCard.tsx` below the question text (only rendered when `answeringGuideline` is non-null, so Core questions show no empty section).

### Executive per-respondent answer drill-down (from `SECOND_REVIEW.md`, Phase 7)

`insights.service.ts`'s existing `getOrganizationQuestionnaireSummary`/`answerDistribution` is aggregate-only (counts per option, no identity) — new `getAnswerDrilldown(organizationId, questionnaireCode)` (`GET /organizations/:orgId/answer-drilldown`, same Executive-own-org/Admin-any-org authorization convention as the other org-scoped insights routes) retains each individual respondent (email, OpCo name/country, workingDomain, designation — "role" per the review maps to these existing free-text profile fields, not the `Role` enum) behind every `(question, subScenario, option)` they chose, scoped to `SUBMITTED` responses only. **This is a deliberate privacy/scope expansion, not an oversight**: it makes individual employees' answer choices visible to their own org's Executive, per the review's own example (a Group CTO comparing NatCo-level responses down to who-picked-what). `ExecutivePage.tsx`'s existing Cognitive-Activity-grouped answer-distribution table got the incremental extension — each option's count cell is clickable (when count > 0) and toggles an inline expanded row listing that cell's respondents, rather than a separate page. ### Submission editing + Admin accepting-window toggle (from `SECOND_REVIEW.md`, Phase 8)

The original locked-forever-on-submit behavior is now conditional on an Admin-controlled accepting-responses toggle. **The toggle itself was originally one global `Questionnaire.acceptingResponses` column, described below as first built — THIRD_REVIEW.md Phase 4 replaced it with the per-organization `QuestionnaireOrgSetting` model described in "Per-organization questionnaire acceptance" above; treat that section as authoritative for the toggle's current scoping/storage, this section for the surrounding submit/resume/re-submit mechanic, which is unchanged.**

- `responses.service.ts`'s four mutation guards (`upsertAnswer`, `deleteAnswer`, `upsertComment`, `submitResponse`) no longer check `response.status !== 'IN_PROGRESS'` (the old `ResponseAlreadySubmittedError`, now removed entirely) — they check the accepting-responses flag instead (`AcceptanceClosedError`, 409). While a questionnaire keeps accepting responses, a `SUBMITTED` response stays fully mutable, including calling `submitResponse` again as a legal **re-submit**: it recomputes the score from whatever answers/comments are current, replaces the prior `ScoreResult` snapshot (`scoreResult.deleteMany` then `create` in the same transaction — a plain `create` would violate the `responseId` unique constraint on a second submit), and updates `submittedAt`. Once closed, every mutation is blocked regardless of the response's own status — matching the original, permanent-lock behavior.
- `QuestionnairePage.tsx`: the hard redirect-to-results for a `SUBMITTED` response fires when accepting responses is false for the user's org; otherwise the user re-enters the question flow with existing answers/comments pre-hydrated (already-supported resume path), sees an info banner ("you already submitted... you can keep editing"), and the Submit button reads "Update submission" instead of "Submit".
- `ResultsPage.tsx`: shows a "Review / edit your answers" link back into `/questionnaire/:code` when still accepting responses, and now also renders the response's comments via `GroupedCommentsList` (previously not shown anywhere outside the pre-submit Review step) — `ScoreBreakdownTable.tsx` (Phase 3) already serves as the per-question "what did I answer" view, so no separate raw-answers table was needed.
- `AdminPage.tsx`'s `QuestionnaireSettingsSection` — originally an assessment selector plus a Close/Reopen button scoped per questionnaire code only; rebuilt in THIRD_REVIEW.md Phase 4 to require an Organization selection too, see above.

### Mandatory sub-scenario tagging and clickable review gaps (from `THIRD_REVIEW.md`, Phases 1-2)

- **A generic "None of the sub-scenarios" comment no longer covers a skip.** `responses.service.ts`'s `submitResponse` coverage check (and `QuestionnairePage.tsx`'s mirrored client-side one) now require `coverage.subScenarioIds.has(subScenario.id)` — `appliesToNone` was dropped from the OR-condition entirely. `appliesToNone` still persists and displays normally; it's just no longer an excuse for an actual gap. ### Per-organization questionnaire acceptance (from `THIRD_REVIEW.md`, Phase 4)

The single global `Questionnaire.acceptingResponses` boolean (SECOND_REVIEW.md Phase 8) didn't fit a multi-org deployment where one organization needs to close a questionnaire without affecting others — it was fully replaced (no shared global default) by a new `QuestionnaireOrgSetting` model: `{ questionnaireId, organizationId, acceptingResponses @default(true) }`, composite-keyed `@@id([questionnaireId, organizationId])`, mirroring `OpCo`'s org-relation pattern.

- **Every (questionnaire, organization) pair is backfilled to `true`** on creation from both directions: `organizations.service.ts`'s `createOrganization` inserts a row per existing questionnaire (in the same transaction as the org itself), and `prisma/seed/seed.ts`'s `seedQuestionnaire` inserts a row per existing organization (`skipDuplicates: true`, idempotent). `questionnaire.service.ts`'s `getAcceptingResponses(questionnaireId, organizationId)` still defensively defaults to `true` when no row exists — load-bearing, since every integration test that creates a throwaway org via raw `prisma.organization.create(...)` bypasses the backfill.
- `questionnaire.service.ts`'s `setAcceptingResponses(code, organizationId, acceptingResponses)` (`upsert`, so it works even if a backfill row is somehow missing) is the write path; `getQuestionnaireByCode(code, organizationId)` resolves the caller's own-org flag for `QuestionnaireDto.acceptingResponses`. New Admin-only `GET /questionnaires/:code/accepting?organizationId=` route added per-route (not via the router's blanket `authenticate`), same pattern as the existing `PATCH` — see the router-mounting gotcha below.
- `responses.service.ts`'s four mutation guards now resolve the flag via a new `assertAccepting(questionnaireId, organizationId)` helper instead of reading `response.questionnaire.acceptingResponses` directly; `organizationId` is threaded in from `req.user!.organizationId` at the controller layer (same JWT-payload-trust convention already used by the `insights`/`opcos` controllers' own-org checks).
- **A real gap this surfaced**: because acceptance is now per-org rather than global, an Admin can close a questionnaire for an organization while one of its users has no prior response yet, or an `IN_PROGRESS` one — previously `QuestionnairePage.tsx`'s closed-questionnaire guard only handled an already-`SUBMITTED` response. It now also renders a plain closed-notice (instead of the question flow) for an `IN_PROGRESS` response once `!questionnaire.acceptingResponses`, and the three per-change mutations (`answerMutation`/`deleteAnswerMutation`/`commentMutation`) gained an `onError` handler that surfaces a 409 as a visible banner and refetches the questionnaire so the guard takes over on the next render — previously a save closed out from under an editing user would fail silently.
- New `frontend/src/components/OrganizationAutocomplete.tsx` (typeahead combobox, client-side substring filter over the existing unfiltered `GET /organizations` list) was built here for `AdminPage.tsx`'s rebuilt `QuestionnaireSettingsSection` (org selector required before the toggle appears) and reused unchanged by the Organization Deep-Dive's benchmarking-table org filter, below.

## Architecture

Monorepo, npm workspaces (plain npm, no Turborepo/Nx): `shared/`, `backend/`, `frontend/`.

- **`shared/`** (`@anlet/shared`) — types/enums only (`Role`, `AnswerOption`, API/score DTO shapes), consumed as TS source directly by both other workspaces (no build step). Keeps frontend/backend from drifting on shared vocabulary. No runtime logic lives here — scoring stays backend-only/authoritative.
- **`backend/`** (`@anlet/backend`) — Express + Prisma + PostgreSQL. Domain modules live under `src/modules/<domain>/{routes,controller,service}`; the scoring engine (`src/modules/scoring/scoring.ts`, Phase 1) is a pure-function module with zero Prisma/Express imports so it's unit-testable without a DB.
- **`frontend/`** (`@anlet/frontend`) — Vite + React + TypeScript, React Router, TanStack Query.
- **Single-host deployment**: one Cloud Run service / one Docker container. `frontend`'s Vite build writes directly to `backend/public` (see `frontend/vite.config.ts` `outDir`); `backend/src/app.ts` serves `/api/*` routes, then that directory as static assets, then falls back to `index.html` for client-side routes. There is no separately-hosted frontend and no CORS layer (same-origin in production). Local dev still runs two processes (Vite dev server + `tsx watch`) for HMR — that's a dev-time convenience, not a contradiction of the single-host production model.
- **Auth**: custom email/password, bcrypt-hashed, JWT in an httpOnly/Secure/SameSite=Lax cookie. No external auth vendor, no self-signup — Admin creates all users (seeded into an internal "Anlet (Internal)" organization; the bootstrap Admin itself comes from `ADMIN_EMAIL`/`ADMIN_PASSWORD` via `prisma/seed/seed.ts`, idempotent).
- **`SubScenario.code` is a plain string, not an enum.** It was originally a fixed Prisma enum (RAN's 5 codes only); Core FM introduced a genuinely new code ("Communication and Quality of Service") and Stability needed a synthetic single sub-scenario, so it was migrated to a free-form string, unique per questionnaire (`@@unique([questionnaireId, code])`). Don't reintroduce a fixed enum here — sub-scenario identities are questionnaire-specific.
- **`Questionnaire.acceptingResponses` no longer exists as a column.** THIRD_REVIEW.md Phase 4 replaced it with a separate `QuestionnaireOrgSetting` join model (`{ questionnaireId, organizationId, acceptingResponses }`, composite PK) so acceptance is independent per organization — see "Per-organization questionnaire acceptance" above. Don't reintroduce a global flag on `Questionnaire` itself.
- **Seed data is questionnaire-agnostic**: `prisma/seed/seed.ts`'s `seedQuestionnaire(parsed: ParsedQuestionnaire)` upserts any questionnaire from the shared `ParsedQuestionnaire`/`ParsedSubScenario`/`ParsedQuestion` shape (`prisma/seed/parsedQuestionnaire.types.ts`); `parseRanFmXlsx.ts` and `parseCoreFmXlsx.ts` (which exports both `parseCoreFaultManagementXlsx` and `parseCoreStabilityXlsx`, since both live in one file) just produce that shape from their respective xlsx files. Adding a future questionnaire means writing one more parser, not touching the seeding logic.
- **Backend modules built so far**: `auth` (login/logout/me — `me` now reads fresh from the DB, not just the JWT payload, so profile completion shows up immediately; `PUT /profile` self-service), `opcos` (list scoped to the caller's own org for any authenticated role, Admin-only create), `organizations` + `users` (Admin-only create, list, and reassign — see "Admin user reassignment" above; `createOrganization` also backfills `QuestionnaireOrgSetting` rows), `questionnaire` (list + read-only structure per code, plus `getAcceptingResponses`/`setAcceptingResponses`, both Admin-scoped-per-organization — see "Per-organization questionnaire acceptance" above; option criteria numbers are included in the response — see "Terminology, weight/criteria visibility..." below for why that changed), `responses` (answer/delete-answer/comment/submit/result, ownership-guarded, mutation guards resolving `QuestionnaireOrgSetting` via a shared `assertAccepting` helper rather than a global flag, plus `getCoreDomainSummary` for the Core Domain combined score, now surfacing both questionnaire codes so the frontend can link to whichever half is missing), `insights` (org-scoped questionnaire summary for Executive/Admin; `getBenchmarkingSummary` for Admin and `getOpCoBenchmarkingSummary` for Executive/Admin, both sharing `computeBenchmarkRows` — now also accumulating `commentCount`; `getAnswerDrilldown` for Executive/Admin, per-respondent — see "Executive per-respondent answer drill-down" and "Admin Organization Deep-Dive" above — now also returning each respondent's own comment plus the full org-scoped comment list — all questionnaire-selectable, see "Multi-level benchmarking" above). `insights` aggregations are scoped to `SUBMITTED` responses only; a group with zero submissions gets `null` averages, never a misleading `0`. `responses.service.ts`'s `getOrCreateResponse` is **single-shot per user per questionnaire**: it returns the user's existing response (whatever its status) rather than creating a new one — this was a real bug caught during manual browser testing (the original version only checked for an `IN_PROGRESS` response, so a `SUBMITTED` one meant "create a fresh one"). What `QuestionnairePage.tsx` does with that existing response now depends on the caller's own-org `acceptingResponses` (see "Per-organization questionnaire acceptance" above): redirect a `SUBMITTED` response to results once closed, show a closed-notice for an `IN_PROGRESS` one, or resume editing while still open.
- **Route-mounting gotcha** (also caught by manual testing, not by tests): a router-level `router.use(authenticate, requireRole(...))` with no path applies to **every** sub-path under that router's mount prefix, not just its own defined routes. Mounting a second router at the same prefix (e.g. `/organizations`) does not give it an independent role check — the first router's blanket middleware intercepts the request first and can short-circuit with a 403 before the second router is ever reached. `organizations.routes.ts` applies `authenticate`/`requireRole` per-route instead of via a blanket `router.use(...)`, since it hosts routes with different role requirements at the same prefix. Relatedly, `responses.routes.ts`'s literal `/core-domain-summary` route is registered **before** `/:id` — an Express wildcard param route registered first would otherwise swallow it as if `"core-domain-summary"` were an `:id`. Check route registration order whenever a new literal path is added alongside an existing `:param` route on the same router.

## Commands

```bash
# Install (workspace-aware)
npm install

# Local Postgres (docker-compose), then copy env files once:
docker compose up -d
cp .env.example .env
cp backend/.env.example backend/.env    # edit ADMIN_EMAIL/ADMIN_PASSWORD/JWT_SECRET as needed

# Apply migrations, then seed (internal org + bootstrap Admin + all 7 questionnaires, parsed
# from RAN_FM.xlsx, CORE_FM.xlsx, IP_FM.xlsx, Transport.xlsx, Fixed_Access.xlsx). Idempotent — safe to re-run.
cd backend && npx prisma migrate dev
cd backend && npm run db:seed

# Dev (backend :4000 via tsx watch, frontend :5173 via Vite, proxying /api -> :4000)
npm run dev

# Lint / typecheck / test (all workspaces)
npm run lint
npm run typecheck
npm test

# Run a single backend test file
npm test -w backend -- src/modules/scoring/scoring.test.ts

# Production-style build + single-host run, without Docker
npm run build && npm start   # serves built frontend from backend/public on :4000 (local) / :8080 (Docker default)

# Docker (single-host image)
docker build -t anlet .
docker run -p 8080:8080 -e DATABASE_URL=... -e JWT_SECRET=... -e ADMIN_EMAIL=... -e ADMIN_PASSWORD=... anlet
```

Note: the backend's default dev port is `4000` (set via `backend/.env`'s `PORT`), not `8080` — chosen to dodge a local port conflict during scaffolding; Cloud Run/Docker still default to `8080` (`env.ts`'s fallback), which is what `EXPOSE`/Cloud Run expect. If `8080` is free on your machine, you can safely set `PORT=8080` locally instead and update `frontend/vite.config.ts`'s proxy target to match.
